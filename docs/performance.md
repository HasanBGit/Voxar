# Performance and load

Everything on this page was **measured on one machine**: an Apple M4 laptop, 10 cores, 16 GB RAM, macOS 15, Python 3.10, CPU only (no GPU), models run from a local cache. Numbers on your hardware will differ. Reproduce them with the scripts in `scripts/` (commands at the end) and report your hardware next to any number you quote.

**Real-time factor (RTF)** is processing time divided by audio duration. Below 1.0 is faster than real time: RTF 0.05 means 20 seconds of audio per second of work.

> **What these numbers are not.** The test audio is **synthetic**: Arabic sentences spoken by the macOS built-in Arabic voice (one voice, Modern Standard Arabic), generated by us. That is good enough to measure speed and to catch plumbing bugs. It says **little about accuracy on real people**, and nothing about Saudi dialect speech. The corpus is small (14 clips). Treat the error rates as a smoke test, not a benchmark.

## Speech-to-text (Moonshine Arabic, tiny streaming)

| Measure | Result |
|---|---|
| Model files | 8 files, 31.1 MB on disk |
| Cold start (first transcription, includes loading the model) | 0.33 s typical; 1.5 s on the very first run after a fresh download (cold disk cache) |
| Warm speed, 3-6 s clips | RTF median 0.054 (about 18x real time), range 0.035 to 0.072 |
| Warm speed, 38 s file | RTF 0.031 (was 0.111 before the long-audio change below) |
| Warm speed, 115 s file | RTF 0.043 (was 0.129) |
| Memory (peak resident) | 294 MB benchmark process; 340 MB after the long files |
| Whole CLI process, `voxar transcribe` | 4 s clip 0.28 s, 38 s clip 1.4 s, 115 s clip 5.3 s (median of 7 runs, including Python start-up, model load and checksum check); `voxar --version` 0.04 s |

### Error rates on the synthetic corpus

Mean over clips, after normalizing diacritics, punctuation and letter forms. WER = word error rate, CER = character error rate.

| Set | Clips | WER | CER |
|---|---|---|---|
| Modern Standard Arabic sentences | 8 | 4.1 % | 0.7 % |
| Saudi-dialect **wording** read by the MSA voice (not real dialect speech) | 4 | 29.2 % | 5.1 % |
| 38 s and 115 s concatenations of the MSA sentences | 2 | | 1.6 % and 4.5 % |

The dialect-worded set is the interesting signal: words like "وش علومك" and "أبغى" are recognized much worse than MSA, even though the voice is clean. A real dialect corpus is needed before saying anything about Saudi accuracy.

## The local server under load

`voxar serve`, 4 s clip, 32 requests per level, a client on the same machine.

| Concurrent clients | Throughput | Median latency | p95 latency | Outcome |
|---|---|---|---|---|
| 1 | 6.98 req/s (27.9 audio s per s) | 0.14 s | 0.16 s | all served |
| 2 | 6.86 req/s | 0.29 s | 0.30 s | all served |
| 4 | 5.49 req/s | 0.63 s | 1.49 s | all served |
| 8 | 6.04 req/s | 1.25 s | 1.58 s | all served |
| 16 | 6.60 req/s | 0.78 s | 1.36 s | 9 served, 23 refused at once with `503` + `Retry-After: 1` |
| 32 | 6.55 req/s | 0.77 s | 1.37 s | 9 served, 23 refused at once |

Run-to-run variation is real: the same configuration (8 clients) gave 6.04 req/s in one run and 6.91 in a later run on the final code, and a repeat of the cold start gave 0.25 s against 0.33 s. Read the throughput column as "about 6 to 7 requests per second", not as a precise figure.

Live WebSocket streams (a 4 s clip):

| Streams | Sent | Time to first text | Final text after "end" | Outcome |
|---|---|---|---|---|
| 1 to 4 | paced at real time (like microphones) | about 1.05 s, flat | 0.03 to 0.18 s | all served |
| 4 | as fast as possible | 0.05 to 0.15 s | 0.64 to 0.82 s | all served |
| 5 and 8 | as fast as possible | | | 4 served; the rest get an error message and close code 1013 |

Text-to-speech through the server: 5.4 to 6.7 req/s for a one-sentence request, with the same overload behavior (503 beyond the queue).

## Design choices behind the numbers

1. **The server runs one job at a time.** Without a limit, throughput was 6.65 req/s with one client but only about 4.5 with two or more, and p95 latency was 5.7 s at 16 clients. Moonshine documents that work on one loaded model is serialized, and we tested whether *separate* model instances would scale: they did not (1 model: 6.82 req/s; 2 models on 2 threads: 5.43; 4 models: 5.00). So each engine has a gate: one job at a time, up to 8 waiting, everything else gets `503` with `Retry-After: 1` immediately.
2. **Long audio is transcribed in coarser chunks.** Feeding 100 ms chunks makes the cost per second grow with file length (RTF 0.042 at 8 s up to 0.114 at 76 s). Chunk size trade-off on the corpus:

    | Audio length | CER at 100 ms chunks | CER at 2 s chunks | Speed at 2 s vs 100 ms |
    |---|---|---|---|
    | 8 s | 0.0 % | 1.5 % | 1.7x faster, less accurate |
    | 18 s | 5.3 % | 5.3 % | 2.0x faster |
    | 28 s | 3.3 % | 2.8 % | 1.6x faster |
    | 38 s | 4.2 % | 3.9 % | 2.4x faster |
    | 57 s | 5.9 % | 5.7 % | 2.5x faster |
    | 76 s | 5.3 % | 5.1 % | 2.9x faster |

    So `transcribe` uses 100 ms chunks up to 15 s and 2 s chunks beyond. Short clips need the fine chunks: at 4 s, going to 5 s chunks raises CER from 2.2 % to 7.1 %. An explicit `chunk_ms` always wins. Live streaming is unaffected (it uses whatever chunks you send).
3. **Moonshine's whole-file mode was tested and not adopted.** It is fastest (RTF 0.015 to 0.024 at every length) but worse on short clips (CER 7.1 % against 2.2 %) and repeats words ("المطعم المطعم"). It could be added later for very long files; the evidence for equal quality on long audio is thin.
4. **A native warning on every start is hidden.** Moonshine's C++ tokenizer printed a harmless notice to stderr on each run. It is held back during model load and shown only if loading fails.
5. **A full WebSocket server answers explicitly.** A refusal at capacity would look like a bare HTTP 403, the same as a security rejection, so the server accepts, sends an explanatory message and closes with 1013.

## Ending a phrase: volume gate versus Silero

How well `listen`, `ask` and `inbox listen` find the end of a phrase, measured with `scripts/turntaking.py` on the Apple M4 above. Four synthetic clips (macOS Arabic voice "Majed", 1 to 6 s long) are placed after 1 s of white noise and followed by 4 s of noise. The silence setting is 1.0 s. Each condition ran 3 times per clip (12 runs), plus 3 runs of noise with no speech at all.

| Noise (RMS of 32767) | Detector | Missed | Cut early | End delay (median) | False start |
|---|---|---|---|---|---|
| 0 | volume | 0/12 | 0/12 | 0.96 s | 0/3 |
| 0 | Silero | 0/12 | 0/12 | 1.06 s | 0/3 |
| 200 | volume | 0/12 | 0/12 | 0.96 s | 0/3 |
| 200 | Silero | 0/12 | 0/12 | 1.06 s | 0/3 |
| 800 | volume | 0/12 | 0/12 | 4.06 s | 3/3 |
| 800 | Silero | 0/12 | 0/12 | 1.07 s | 0/3 |
| 1500 | volume | 0/12 | 0/12 | 4.06 s | 3/3 |
| 1500 | Silero | 0/12 | 0/12 | 1.13 s | 0/3 |

Reading it: in a quiet room the two are equivalent (Silero ends about 0.1 s later). Once steady noise passes the volume gate's fixed level, the gate takes the noise for speech: it never sees silence, so capture runs until the stream ends (4.06 s after the speech) and noise alone "finds a phrase" every time. Silero still ends within 0.1 s of the silence setting. The end delay is the time from the end of the clip to the end of capture; it can sit slightly under the silence setting because the clips end in a quiet tail.

Limits: one synthetic voice, white noise (not a street, a fan or other voices), clean speech with no overlapping speakers, and no real microphone. This shows the logic works and where the volume gate breaks. It does not say how either detector behaves for real people in real rooms.

## Speaking a long message

`announce`, `ask` and `voxar say` play one sentence while the next is synthesized. First-sound time with the Saudi voice on the Apple M4 above (median of 5 runs, voice already loaded, a stand-in player that returns at once):

| Message | Before (all synthesized first) | Now (first sentence only) |
|---|---|---|
| 4 sentences, 174 characters | 0.83 s | 0.24 s |
| 1 sentence, 47 characters | 0.25 s | 0.24 s |

A one-sentence message gains nothing. Run-to-run variation is real (an earlier run of the same 4-sentence message took 0.50 s the old way), so read the table as "a few tenths of a second saved on multi-sentence messages", not as precise figures. Separately, loading the voice takes about 3.8 s on its first use, which `voxar mcp --voice` now pays at start-up.

## Reproduce it

```bash
# speed, memory and (with --refs) error rates; use your own 16 kHz mono WAV files
uv run python scripts/benchmark.py asr clips/*.wav --refs refs.json --repeat 3
VOXAR_SYNTHESIZER=nabra-saudi python scripts/benchmark.py tts "مرحبا" "يا أهلاً وسهلاً" --repeat 3

# server load: start `voxar serve`, then
uv run python scripts/loadtest.py http  --file clip.wav --concurrency 8 --requests 32
uv run python scripts/loadtest.py ws    --file clip.wav --streams 6 --realtime
uv run python scripts/loadtest.py speak --text "مرحبا" --concurrency 4 --requests 24

# ending a phrase, volume gate vs Silero (Silero needs `uv sync --extra vad` and `voxar models pull silero-vad`)
uv run python scripts/turntaking.py clips/*.wav --noise 0 200 800 1500 --silence 1.0 --repeat 3
```

`refs.json` maps a clip's file stem to its reference text. The scripts print the machine they ran on.

## Not measured

Real human speech and any dialect corpus; accuracy on noisy audio or phone calls; the live microphone path (the table above feeds recorded audio through the same code); GPU or other CPUs; memory growth over hours; the server under network latency; more than one voice.
